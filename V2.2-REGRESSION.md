# MeshCore 64 v2.2 — regression

Every run is **2400 baud**, the same 13361-byte build, in VICE against a
fake radio that pushes a channel message every four seconds.

2400 only. It is the tightest bit period the driver has to hit — 411
cycles on PAL, 426 on NTSC — so a build that passes there cannot fail at
600 or 1200 for any timing reason. Running the slower rates spends an hour
to learn nothing.

## Reading the columns

| column | meaning | fails a run? |
|---|---|---|
| rej | frames rejected | **yes** |
| framing | framing errors on the wire | **yes** |
| handshake | stage reached; `0F` is complete | **yes** |
| unknown | unrecognised opcodes | no |
| hdr bad | frames rejected at the length header | no |
| ring hw | deepest the 256-byte receive ring got | no |
| archived | lines written to the scrollback (REU runs) | no |

**`ring hw` is a high-water mark, not an overrun count.** `poll` records
`max(RHEAD - RTAIL)`; nothing is ever dropped. Read it as headroom — 35 of
256 is 14% full, which is how much margin the driver has at 2400.

**`unknown` and `hdr bad` are two sides of one known effect.** `sendfr`
masks the receiver for the duration of an outgoing frame, so an unsolicited
push that arrives mid-send is clipped. The clipped frame is dropped, and
MeshCore's sync is a pull model — the message is fetched on the next round.
Neither counter existed when the v2.01 matrix ran, so there is no baseline
for them.

## What this does not cover

None of v2.x has been run against real hardware. `latadj` — the 275-cycle
allowance for NMI entry latency — was tuned in the emulator, and it is the
one constant most likely to need re-tuning on a real machine.
