# s3.1 FIRST REAL-HARDWARE RESULT: 2400 probe (mc64-2400-rxfix-probe-2400-test)
- Date: 2026-10-10
- Goal: run the 2400-baud probe on the user's real NTSC C64 + 2400 firmware.
- What the user reported (verbatim): "This is the 2400 probe" + a photo (shots/hw-2400-probe-photo-1.jpg). Screen text, transcribed:
  ```
  MESHCORE 64 V2.3.4D
  RX PROBE 2.3.4D  BT/HB: 01a9 016c
  TRY 1  N=44 FE=02     12 01 05 01 16 16 94 91 96 7a 3a 6b   fail NOT A SELFINFO HEADER
  TRY 2  N=44 FE=02     12 01 05 01 16 16 94 91 96 7a 3a 6b   fail
  TRY 3  N=44 FE=02     12 01 05 01 16 16 94 91 96 7a 3a 6b   fail
  GOOD REPLIES (OF 3): 00   WANT 3E XX 00 05
  ```
- Result: PARTIAL SUCCESS. This is the first time in the whole effort that our receiver has produced real data on hardware (before: all 00, or ~16 junk bytes).
  * N=0x44=68 bytes in each try, identical every time. A SELF_INFO frame is 3 header + 66 payload = 69 bytes.
  * Bytes 3.. (`05 01 16 16 ...`) are correct: 05 = SELF_INFO, 01 = adv type, 16,16 = tx power 22/22 dBm (matches the radio log earlier: "TX POWER -> 22 dBm").
  * Only the FIRST bytes are wrong: expected `3e 42 00 05`, got `12 01 05`.
- Diagnosis (checked bit-exactly, not guessed): if the receiver MISSES THE START BIT OF THE VERY FIRST BYTE (3E), the next falling edge is the 1->0 inside 3E's data (bit 6), taken as a "start". Sampling from there gives exactly 0x12 (and a stop bit of 0 -> framing error), the next byte exactly 0x01 (another framing error), and then it is back in step on 0x05. That is `12 01 05 01 16 16` with FE=2, which is what the photo shows. (Python model in this session's transcript; reproduces output and FE count exactly.)
  So: timing is fine at 2400 (latadj 275, +-0 tuning needed so far), mask fix works. The remaining bug is that the reply's first start bit is lost.
- Likely cause: the radio starts replying very soon after our last stop bit -- maybe even before it ends, because the ESP32 UART decodes our last byte at the middle of the stop bit. Our receiver is switched off for the whole of sendfr and re-armed with an ICR clear (`lda C2ICR` discards a FLAG latch); txwait also reads (clears) the ICR every ~10 cycles during the stop bit. Either path can swallow the first start edge. VICE showed the same symptom with its instant fake radio (s2.4: tries 2/3 `42 00 05`, 3E missing) -- I had written that off as a fake-radio artifact; it was the same bug.
- Not hardware-verified yet: the cause above. Next step is to model the radio answering at different delays in the sim and fix sendfr (arm FLAG before the final stop bit, no ICR reads during it, no ICR clear on exit).
- Surprises: plan said TX path should not be touched; the evidence now requires a change in sendfr's exit and last stop bit only (the ICR-poll TX of the 8 data bits is hardware-proven at 2400 -- the radio answered it).
