# s3.6 BUG (user-found on hardware): hashtag channels added on the C64 get an all-zero key
- Date: 2026-10-10
- What the user reported (verbatim):
  "One bug I see with this build, I can send and receive messages in the public channel. It can scan the other channels, but I can't actually send and receive messages in those other channels."
  "One note, I built the channels using the app on the Commodore. Maybe it built them weird or with weird characters or something like that."
  "And I built just hashtag channels."
- Also implied: the FULL CLIENT at 2400 baud works on real hardware (Public send+receive, channel scan) -- the first full-client run on our own driver.
- Root cause (confirmed from source, not guessed): MeshCore derives a hashtag channel's secret as the FIRST 16 BYTES OF sha256(name incl. '#') -- docs/companion_protocol.md "Channel Types" (#test -> 9cd8fcf22a47333b591d96a2b848b73f, verified with hashlib). The firmware does not derive it; the CLIENT must. Our addchan (ml/mlfull.py ~3076) says "A leading # is just part of the name; nothing special is needed here", and inphx leaves SECBUF all zero on an empty key field. So the radio holds '#name' with key 00..00: our sends are unreadable to everyone, and everyone else's '#name' traffic fails to decrypt and is dropped. Public works because its key is fixed.
- Scope: pre-existing in every version with "add channel" (not related to baud rate or the receiver work).
- Fix plan: 6502 SHA-256 (single 64-byte block; name <= 31 bytes) in segment 2 (4037 bytes free), used when the name starts with '#' and the key field is empty; verify against hashlib in py65 before any cart. Workaround meanwhile: remove + re-add each channel typing the 32-hex-digit key.
