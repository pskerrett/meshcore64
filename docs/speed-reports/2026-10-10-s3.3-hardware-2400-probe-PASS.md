# s3.3 HARDWARE PASS: v2.3.5d probe at 2400 baud on the real C64
- Date: 2026-10-10
- Goal: confirm patch234 (ICR mask) + patch235 (don't lose the reply's first start bit) on real silicon at 2400.
- Build: mc64-v2.3.5d-probe-2400-test.crt (FTP share), radio on the 2400 firmware, user's real NTSC C64.
- What the user reported: a photo, no text (shots/hw-2400-probe-v2.3.5d-PASS.jpg). Screen transcribed:
  ```
  MESHCORE 64 V2.3.5D
  RX PROBE 2.3.4D  BT/HB: 01a9 016c        (probe banner text not bumped; build is v2.3.5d)
  TRY 1  N=45 FE=00   3e 42 00 05 01 16 16 94 91 96 7a 3a   pass SELFINFO AT OFFSET 00
  TRY 2  N=45 FE=00   3e 42 00 05 01 16 16 94 91 96 7a 3a   pass SELFINFO AT OFFSET 00
  TRY 3  N=45 FE=00   3e 42 00 05 01 16 16 94 91 96 7a 3a   pass SELFINFO AT OFFSET 00
  GOOD REPLIES (OF 3): 03   WANT 3E XX 00 05
  ```
- Result: PASS.
  * N=0x45 = 69 bytes = a complete SELF_INFO frame (3 header + 0x42 payload) in every try; before (s3.1) it was 68 with 12 01 05.
  * FE=00: no framing errors; the 12 bytes shown are identical in all three tries and equal to the bytes seen (correctly) from byte 4 on in s3.1 (94 91 96 7a 3a ...).
  * Timing 01a9/016c = 425/364 cycles, i.e. latadj 275 unchanged: no hardware tuning was needed.
  * This is the first time our own RS-232 driver has received a frame on the real cart, at any baud rate, in this whole project. Receive = 4x the old 600 rate.
- What it proves / does not:
  proves: the ICR-mask root cause (s1/s2) and the lost-first-start-bit cause (s3.1/s3.2) were both real, and the sim's model of the 6526 was right about them.
  does not prove: sustained reliability. This is 3 short exchanges, 207 bytes. Not yet shown: the full client, a multi-minute soak, a busy mesh (back-to-back LOG_RX_DATA pushes up to 176 bytes with no flow control), PAL machines, sending long messages, margin of latadj on hardware (window in the sim is only 240-320).
- Surprises: none. (Cosmetic: the probe's own title string still says 2.3.4D.)
- Next (plan Stage 3.3/3.4): user runs the full client at 2400 (mc64-v2.3.5d-2400-test.crt) for 30+ minutes on the live mesh and reports F3 counters / anything odd; I check the VICE regression (logs/regression-v2.3.5d.log) and, if wanted, build the on-hardware latadj margin sweeper (Stage 3.2) to measure the real pass window.
