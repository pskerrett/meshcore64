# s3.4/s3.5 VICE: driver builds crawl through the channel scan (old AND new) -- harness issue, not hardware
- Date: 2026-10-10
- Seen: full client on our own driver in VICE stalls/crawls in the boot channel scan.
  * 2400, reu, 200M cycles: v2.3.3d (original driver), v2.3.4d, v2.3.5d all IDENTICAL: 16 commands, stuck after GET_CHANNEL 11 ("SLOT 11/40"), 0 message syncs, queue 42 (logs/radio_s3_4_*.log, shots/shot_s3_4_*.png). 320M cycle run of v2.3.5d: same, queue 71.
  * 600, reu, testk=1, 175M: driver builds (old and new) still at "SLOT 3/40", never reach the scripted picker keys, so no `cmd 3` sends; the KERNAL v2.3.3 build finishes the scan and sends "hi" (logs/radio_s3_5_chan_*.log).
- Conclusion: pre-existing (present in the untouched v2.3.3d driver), NOT caused by patch234/235. And on REAL hardware the v2.3.5d full client at 2400 scans channels and sends/receives in Public (user report, s3.6). So this is a VICE/fake-radio artifact of the driver builds.
- Suspected mechanism (UNVERIFIED): VICE rsuser.c only delivers an incoming byte when its RTS input matches (`int_rsuser`, case 0: `(rsuser_rtsinv ? 0 : RTS_OUT) == rts`). Driver builds leave PB1 (RTS) as an input (DDRB=120); the KERNAL builds drive it. Same VICE behaviour that throttled fixE in Sep. Fix would be harness-side (e.g. -rsuserrtsinv / modelled RTS), not client-side -- do not change the client for VICE.
- Consequence: VICE cannot currently be used for long scripted UI tests of the driver builds; use the KERNAL build for UI/logic tests (identical code above the serial layer) and the sim + hardware for the driver.
- Next: investigate VICE RTS gating only if a driver-build UI test is needed.
