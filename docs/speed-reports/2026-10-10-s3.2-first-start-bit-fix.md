# s3.2 Fix: don't lose the first start bit of the radio's reply (patch235.py, v2.3.5d)
- Date: 2026-10-10
- Goal: the hardware probe (s3.1) showed every reply losing its first start bit. Model it, fix it, prove the fix in the sim.
- Changed:
  * ml/rxsim.py: two CIA timers (A and B), TXD logging, and a `--tx` mode that runs the real `sendfr`, then has the "radio" start its 69-byte reply at a chosen delay relative to the END of our last stop bit (-1.0 .. +2.0 bit). Pre-edit copy: ml/rxsim-v1.py.
  * ml/patch235.py (applied; snapshot builds/patch235.py.snapshot) -> ml/mlfull.py, ml/mkkernal.py. Pre-fix snapshots: ml/mlfull-v2.3.4.py, ml/mkkernal-v2.3.4.py. Banner v2.3.5d.
    - last stop bit of a frame only (new TXLST flag): clear ICR once, arm FLAG (NMIEN=$10, mask $90), then wait by watching timer A's HIGH byte (new txwaitc, from ml600fd) -- no ICR reads;
    - sendfr's exit no longer does `lda C2ICR` / re-arm (that discarded a latched start edge);
    - the ICR-polled txwait for all other bits is untouched (hardware-proven at 2400 by the s3.1 result: the radio answered it).
- Commands: `V/bin/python -I ml/rxsim.py --src ml/mlfull-v2.3.4.py|ml/mlfull.py --baud 2400 --tx --badlines 0`; `txcheck.py` (decodes the TXD waveform from the PRA log).
- Result (sim): PASS.
  | version | reply start times lost (of 160, 2400 baud, -1.0..+2.0 bit) | lost window |
  |---|---|---|
  | v2.3.4 sendfr (old) | 59 | from before our stop bit ends up to about +0.1 bit (+40 cycles) -- exactly where a UART that decodes at mid-stop-bit would answer |
  | v2.3.5 sendfr (new) | 3 | only -1.00..-0.96 bit, i.e. reply starting in the first 16 cycles of our stop bit, before the radio could have received it (impossible; the earliest real answer is ~-0.5 bit) |
  logs/rxsim-tx-sweep-OLD-sendfr-2400.log, logs/rxsim-tx-sweep-NEW-sendfr-2400.log
  Transmit integrity: TXD decoded from the PRA log is byte-exact `3c 0b 00 01 00.. 43 36 34` at 600/1200/2400 for BOTH versions (logs/txcheck-sendfr-old-vs-new.log).
  The KERNAL (600) build still assembles after the patch.
- Not proven: hardware. Everything above is the sim's model of the 6526/ESP32 timing.
- Surprises: (1) A first attempt at the sweep monitor looped forever because its `pgrep -f` pattern matched its own command line -- use `kill -0 PID`. (2) An earlier tool call that the user interrupted had in fact already applied a patch to rxsim.py, and re-running it applied it twice (duplicate argparse option); fixed by removing the duplicate blocks and re-running the rx test. (3) In s2.4 I called the VICE "42 00 05" symptom a fake-radio artifact; it was this bug.
