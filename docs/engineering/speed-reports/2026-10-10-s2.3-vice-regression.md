# s2.3 VICE regression: v2.3.4d (fixed) vs v2.3.3d (old), NTSC, 600, driver builds
- Date: 2026-10-10
- Goal: functionality regression only (VICE cannot judge receive: it pulses FLAG once per byte, see s1.1).
- Commands: `build231/run.sh <prg> <tag> 130 {reu|noreu}` on builds/mc64-v2.3.3d-600-old.prg and builds/mc64-v2.3.4d-600.prg (md5 in builds/md5.txt). Logs: logs/radio_s2_3*.log, shots/shot_s2_3*.png.
- Result: PASS, with a caveat about noise.
  | run | getchan | sent17 (msg syncs) |
  |---|---|---|
  | old reu | 5 | 13 |
  | new reu | 5 | 13 |
  | old noreu | 1 / 5 (repeat) | 23 / 13 |
  | new noreu | 9 / 3 (repeat) | 20 / 20 |
  REU runs are identical. no-REU runs vary run to run even for the OLD build (old noreu getchan 1 then 5), so those two counters are timing noise (where the boot scan is at the 130M-cycle cutoff), not a regression signal. Screenshots of both builds show a connected client: backlog messages, `+N>` prompt; the new build also reached the channel scan.
- Caveat: no hand-check of every feature (F1/F3/F5 etc.); patch234 touches only the receive handler, the mask bookkeeping in sendfr, and the timer constants, so a full feature campaign was judged out of scope here.
- Surprises: new build screen shows `RADIO ?` (node name unset) -- the long-known "app_start reply not assembled" symptom (memory: meshcore64_cart_hardware, ML client section); cannot tell if old had it (old screenshot scrolled). Not caused by this patch (same code path).
