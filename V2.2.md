# MeshCore 64 — v2.2 beta

**A proper interface, now that there is room for one.**

> **This is the `v2.2-beta` branch.** The stable client is the BASIC one on
> [`main`](https://github.com/pskerrett/meshcore64/tree/main) — v1.2d, 600
> baud, proven on real hardware. v2.x has only been tested in an emulator.
>
> Hardware setup, firmware flashing and the companion patch are unchanged —
> see [README.md](README.md).
>
> **Flash the 2400-baud firmware.** v2.2 talks at 2400 and nothing else.
> The 600-baud firmware environment still exists because that is what
> v1.2d on `main` pairs with — flash that one and v2.2 will not connect
> at all. The matching build ships with this branch as
> `meshcore64-ble-2400-*.bin`.

---

## What v2.2 adds

v2.01 was the rewrite: BASIC out, machine language in, our own RS-232
driver, 2400 baud with the display on. It kept v1's interface, which was a
scrolling terminal and a channel picker.

**2400 baud is now the only speed.** v2.01 shipped 600/1200/2400 as build
options; v2.2 defaults to 2400 and tests nothing else. 2400 is the tightest
bit period the driver has to hit, so a build that passes there cannot fail
at 600 for any timing reason — running the slower rates through the matrix
spends an hour to learn nothing. The slower constants are still in the
table, because the bit period is a build-time value either way and it
costs nothing to leave a way back if real hardware disagrees with the
emulator.

v2.2 spends the room that rewrite bought on the interface.

| | v2.01 | **v2.2** |
|---|---|---|
| Client size | 5,322 bytes | **13,600 bytes** |
| Interface | scrolling terminal | **pop-up menus, panels** |
| Start-up | text banner | **hires splash** |
| Radio config | — | **live, from the node** |
| Node list | — | **contacts, routes, DMs** |
| Telemetry | — | **login + Cayenne LPP** |
| Channels | picker only | **add, edit, remove** |
| Channel picker | plain text list | **same frame as everything else** |
| Scrollback, no REU | 24 lines, `F5` off | **409 lines, `F5` works** |
| Contacts | 32 stored, 12 reachable | **96 with an REU, all reachable** |
| Link speed | 600/1200/2400 | **2400, and only 2400** |

### F1 opens a menu

Everything hangs off one pop-up, drawn in the frame-and-colour style the
old BBS terminals used:

```
 ┌─ meshcore ──────────────┐
 │ channels                │  red
 │ nodes                   │  yellow
 │ stats                   │  cyan
 │ radio config            │  purple
 │ add/remove channel      │  light green
 │ close                   │  light blue
 └─────────────────────────┘
```

**The link keeps running behind it.** Every key loop in the client — menu,
panel, text field — calls `poll` and dispatches whatever arrives, so
messages are still received and archived while a menu is open. They are
not *printed*, because printing at the bottom of the screen scrolls it and
would drag the menu off the top; a `UIMODE` flag suppresses output and the
unread counter is redrawn when the menu closes.

### The start-up screen

Reports what the client found before it says anything else: the video
standard it measured, the REU it detected and how big, then — once the
link is up — the node's own name and firmware version, and what the
function keys do.

The first two are known from `detpal` and `reudet` without the radio, so
they print before `connecting...`; the node name comes from `SELF_INFO`
and the version from `DEVICE_INFO`, so those wait for the handshake.

### Colour in the chat

Each line is `[room] sender: message`, and the three parts are coloured
apart. The sender's colour comes from a hash of their own name, so the
same person is the same colour from one line to the next without keeping
a table of who is who.

One trap worth recording: colour codes pass through `CHROUT` without
moving the cursor. The prompt-padding logic used to count the bytes it
printed, which would now count the colour codes and pad short — it takes
the length from `CLEN` instead.

### The channel picker

Restyled into the same frame as everything else, but it keeps its own key
loop rather than calling the shared menu code — the digit shortcuts are
worth having. `F1 2` has been how you change channel since v1 and there is
no reason to make people arrow to it instead. Cursor keys, RETURN, `r` to
rescan and `F1` to back out all work alongside. The cursor opens on the
channel you are already in, and a star marks it, because where the cursor
is and where you are are not the same thing.

### Radio configuration

Frequency, bandwidth, spreading factor, coding rate and TX power — the
settings a phone app writes over Bluetooth. The screen opens showing what
the node is *actually* set to, read from the `SELF_INFO` frame the node
sends at handshake, and RETURN steps each field through its presets.
"apply to node" writes them back with `SET_RADIO_PARAMS` and
`SET_RADIO_TX_POWER`.

Units are not uniform and the firmware is the authority: `SELF_INFO`
reports frequency in kHz and bandwidth in Hz, and `SET_RADIO_PARAMS` takes
the same, so values round-trip unchanged.

### Nodes

`GET_CONTACTS` fills a list; picking one offers:

- **send message** — typing now goes to that contact as a direct message
  rather than to the channel
- **log in** — prompts for a password and sends `SEND_LOGIN`
- **telemetry** — `SEND_TELEMETRY_REQ`, and the Cayenne LPP response is
  decoded into a panel
- **show route** — the stored path, hop by hop, or "none - will flood"
- **wipe route (flood)** — `RESET_PATH`, so the next message floods

### Channels

Add, edit or remove any of the 40 slots. A channel needs a name and a
128-bit key; the firmware does not derive one from the name — it only
hashes the key to get the channel hash — so the 16 bytes are typed in as
hex, the same key a phone app shows. A short key is zero-filled, which is
what an unencrypted channel wants. A leading `#` is just part of the name.

Only the 16-byte form of `SET_CHANNEL` is accepted; the firmware answers
the 32-byte variant with `ERR_CODE_UNSUPPORTED_CMD`.

### Stats

Battery and storage from the node, and the client's own link counters:
frames received, frames rejected, unrecognised opcodes, bad headers,
framing errors and ring overruns. Those last ones are what actually
diagnose a marginal link.

### The splash

A 320×200 hires bitmap: the MeshCore wordmark, "64" in the character ROM's
own font, and a drawing of a breadbin. It is generated by `mksplash.py`
and RLE-packed to about 2.8K.

Two details worth recording, because both cost a debugging session:

- **It runs in VIC bank 1.** The bitmap needs 8K somewhere, and putting it
  at `$2000` put it on top of the program as that grew. `$DD00` bits 0-1
  select the bank and are *inverted*; bit 2 is our TXD, so that write must
  be read-modify-write.
- **Colour comes from a 25-byte table**, one foreground per screen row,
  fanned out across 40 cells at run time. In hires the colour lives in the
  video matrix — high nibble for the 1-bits, low nibble for the 0-bits —
  and shipping all 1000 bytes would have cost more than the artwork.

## Text input

Everything above needed one missing piece: a field you can type into. It
is a one-line box that keeps two copies of what is typed — PETSCII to draw
and ASCII for the wire — because converting per keystroke is invisible and
converting a whole line at send time is not. RETURN accepts, F1 cancels,
DEL backspaces, and the loop polls the link so nothing is missed while you
are typing.

It holds 32 characters, which is not arbitrary: a 128-bit channel key is
exactly 32 hex digits, and an earlier 24-character limit made the headline
channel feature impossible to use. The function keys are 133-136, inside
the printable range, so they have to be caught before the range test or
they land in the field as garbage — the same trap the chat input already
carried.

One rule it forced: **a command frame cannot be built before a keyboard
loop and sent after it.** Dispatching an incoming `MSG_WAITING` sends a
sync request, which overwrites the transmit buffer. Channel names are
staged elsewhere and the frame is assembled immediately before `sendfr`.

## The cartridge lamps

They flash on activity as they always did — a ripple on receive, all four
at once on send. What is new is what they do the rest of the time: the
four lamps show **how many messages are waiting, in binary**, least
significant bit on PB3. Four lamps reach 15; beyond that it pins there,
which still reads as "a lot". The count is the same one the prompt shows
as `Public +3>`.

It is written only when the count changes, so the main loop is untouched
otherwise.

A six-lamp version is in the source, commented out. PB1 and PB2 would
carry two more bits and take the count to 63, but they are RTS and DTR:
`DDRB` has to become 126, and VICE's userport RS-232 drops the link the
moment either is driven, so no emulator test can pass with it enabled. On
the real cartridge those pins go to lamps with nothing listening, and
bit-zeal's meshtastic64 drives all six — so it ought to work. Untested on
hardware, which is why it is commented rather than switched on.

The four-lamp version cannot reach those pins even by accident: the count
is masked to 15 and shifted left three, so the largest value written is
120, which is bits 3-6 only.

## Memory, with and without an REU

A C64 with no REU had **23K of free RAM doing nothing** while scrollback
was switched off entirely. That was the wrong trade, and it came from
treating "no REU" as "no archive" rather than "a smaller one".

The archive's region bookkeeping was always generic — only the transfer
was REU-bound. Both transfer points now take a RAM path when there is no
REU, copying to and from the reclaimed splash area at `$4000`, which is
16K free the moment the splash is done.

|  | with an REU | without |
|---|---|---|
| archive | 9 regions x up to 512 lines | **1 merged region, 409 lines** |
| `F5` | yes | **yes** (was: disabled) |
| contacts | **96** | 32 |

Nine regions do not fit in 16K — at 64 bytes a slot that is 28 lines each,
barely better than the 24-line ring it replaces. So without an REU there
is **one merged region**, and every line in it already carries a `[room]`
prefix, which is what makes a merged feed readable. Per-channel history is
what does not fit, not scrollback itself.

Two things this turned up:

- `arcmsg` and `arcown` each write twice, once to the channel and once to
  the merged region. Without an REU both resolve to the same region, so
  the second write had to be skipped or every line would be stored twice.
- **The node list capped at twelve entries** and used the highlight index
  directly as the contact index, so contacts 13-32 were stored and
  unreachable. Raising the cap would have achieved nothing without fixing
  that first; the list now scrolls.

The old 24-line ring and its replay code are gone, which is why the client
got *smaller* while gaining the feature.

## Two character sets, and a trap

The client keeps text in two encodings and it matters which one a routine
wants. `conv()` turns the ASCII that arrives from the radio into PETSCII
for `CHROUT`; `a2s()` turns ASCII into screen codes for the menu drawer.
Running a string through both — which is what happens if a menu draws a
buffer that was already converted for printing — silently uppercases every
letter. It did exactly that to contact names and to channel names.

It caught the text input field too, and there the symptom was worse than
cosmetic: a typed `c64` displayed as `C64` while the lowercase form went
out on the wire. What you saw was not what you sent.

The three are fixed differently, on purpose:

- **Contacts** are read straight from the raw frame, because nothing else
  uses them.
- **Channel names** stay PETSCII, because the bottom prompt and the
  `[channel]` prefix on archived lines both print them with `CHROUT`. The
  picker converts back at the point of use rather than keeping a second
  copy of every name.
- **The input field** now keeps one buffer, in ASCII. It had two, copied
  from the chat input — but the chat needs a PETSCII copy because it
  echoes with `CHROUT`, and this field does not echo at all. The second
  copy existed only to be converted twice.

## Build-time checks

Five assumptions are now checked when the client is assembled, because
each one had already broken silently once:

- **Zero-page pointers.** `(ptr),y` only exists for zero page; the
  assembler emitted a plausible opcode for `$CFA7` and the machine hung.
- **Overlapping regions.** A seven-line panel buffer reached into the
  pointer table that indexed it. The check was rewritten to cover every
  indexed buffer whose size is known for certain, and immediately found a
  second one: the 32-byte channel-name staging buffer ran into the
  firmware version string, so a name longer than sixteen characters
  overwrote it and an incoming `DEVICE_INFO` corrupted the name being
  typed.
- **The program must end below `$4000`**, where the splash bitmap is
  unpacked. The artwork roughly doubled the image, and there are now 735
  bytes of headroom. When that runs out the fix is to unpack the bitmap
  to `$6000` and move the colour map to `$4000` — both are legal
  positions within VIC bank 1 and it buys about 8K.
- **The LPP label strings must share one page**, because the telemetry
  decoder addresses them by low byte alone.

## What is not proven

Everything here has been exercised in VICE against a fake radio. None of
v2.x has been run against real hardware.

The one known-unfixed fault carried over from v2.01: about one run in
fourteen misses a handshake acknowledgement, waits out a ~30 second
timeout, then works normally. Root cause not established.
