## What changed

v1.x is BASIC plus a small machine-language helper, and it runs at **600
baud** because that is the fastest the C64's KERNAL RS-232 routines can
receive reliably. v2 replaces both halves:

| | v1.2c (BASIC) | **v2.01 (machine language)** |
|---|---|---|
| Client | BASIC + 346-byte ML helper | **all machine language** |
| Size | 13,180 bytes | **5,322 bytes** |
| Serial | KERNAL RS-232 | **our own driver** |
| Speed | 600 baud | **600 / 1200 / 2400** |
| PAL/NTSC | KERNAL's problem | **detected at boot** |

**2400 baud with the display on** is the headline — four times the
throughput, on a link that carries 60 bytes per second shared with
everything the radio reports.

## Why the KERNAL could not do it

The C64 has no UART on the user port. The KERNAL bit-bangs RS-232 receive
in an NMI handler, sampling each bit in software and guessing where its
centre falls. Two things break that above 600 baud:

**Badline DMA.** Every eighth raster line the VIC-II steals ~40 cycles from
the CPU. At 600 baud a bit lasts 1642 cycles and 40 is noise. At 2400 a bit
is 411 cycles, and a badline lands during roughly every bit.

**A one-shot timer reloaded per bit.** The KERNAL reloads its bit timer
inside the handler, so the handler's own latency is added to *every* bit
and the error accumulates across the byte until the last samples fall
outside their bits.

v2 fixes the second and rides out the first:

- **Both bit clocks run CONTINUOUS, not one-shot.** The CIA generates bit
  boundaries in hardware, so interrupt latency shifts *where inside a bit*
  we sample but never *where the bits are*. Error stops accumulating.
- **Receive and transmit no longer share an interrupt.** The KERNAL
  services both from one NMI, so a byte going out disturbs a byte coming in
  — and this protocol sends a sync after every single message. v2 masks the
  receiver for the duration of a frame and restores it after. Deliberately
  half duplex, which is what the protocol actually is.
- **Transmit timing comes from a hardware timer, polled.** Badlines cannot
  stretch a bit the way they stretch a counted delay loop.

### The one constant that matters

The first bit is sampled 1.5 bit-periods after the start-bit interrupt,
minus an allowance for how long it takes to *get into* the handler. That
allowance is the whole ballgame:

| latency allowance | 2400 baud result |
|---|---|
| 20 cycles | dead — nothing received |
| 85 *(calculated by hand from instruction timings)* | dead |
| 150 | partial, 9 frames rejected |
| **250–300** | **clean — zero rejected, zero framing errors** |

The measured value is **~275 cycles** against ~68 by hand-counting. At 600
baud that error is 4% of a bit and invisible; at 2400 it put the sample on
a bit *boundary*, where badline jitter tipped it into the neighbouring bit.
It is exposed as the `latadj` build parameter precisely because it is
likely to need re-tuning on real hardware.

## PAL and NTSC

PAL runs at 985248 Hz, NTSC at 1022727 — 3.8% apart. A bit period computed
for one is 3.8% wrong on the other, which compounds across ten bits to
about a third of a bit. Fatal.

v2 carries both sets of constants and **times one video frame at boot** to
choose: PAL is 312 lines × 63 cycles, NTSC is 263 × 65, and a down-counting
timer separates them cleanly (`$B3` vs `$BD`).

Two bugs found writing that, both of which would have shipped:

- Starting the timer *before* waiting for raster line 0 measured "time to
  reach line 0, **plus** one frame" — variable per boot. PAL intermittently
  measured as NTSC and frames were then rejected at random, which looks
  exactly like a flaky link rather than a detection fault.
- Reading `$D011` before `$D012` is a raster race: catch the 255→256
  boundary and you see raster bit 8 clear (line 255) together with a low
  byte of 0 (line 256) — indistinguishable from line 0. That false hit
  ended the measurement after eight lines.

## Ceilings

| baud | screen on | note |
|---|---|---|
| 600 / 1200 / 2400 | ✅ | zero rejected frames, zero framing errors |
| 4800 | ❌ | bit is 205 cycles; handler needs ~70, badline takes 43 |
| 9600 | — | needs UP9600's hardware |

**UP9600 is not reachable in software.** Its shift clock is generated by
the C64 (Timer B pulsing PB7) but must be **bridged externally** back into
CNT2 — three solder bridges: PB0→SP2, PB0→FLAG2, PB7→CNT2. Without the
third wire the CIA shift register has no clock. The faster terminals —
over5 at 38400, Retroterm at 57600 — all run with the **screen off**,
sidestepping badlines rather than solving them.
([pagetable.com](https://www.pagetable.com/?p=1656))

## Features

Everything the BASIC client does:

- Chat on the mesh; messages appear as they arrive
- `F1` channel picker — scans the radio's channel list, shows unread counts
  per channel, marks where you are, `R` re-scans all 40 slots
- An **All** entry merging every channel, each line tagged with its origin
- `F7` jump to Public · `F3` link status
- Per-channel unread counters; the prompt shows `+N` waiting elsewhere
- **REU scrollback** — with a RAM Expansion Unit every message is archived
  per channel; `F5` pages back, `F7` forward, red border while in history
- Without an REU, the last 24 messages are kept in RAM and replayed on a
  channel switch
- Cartridge LEDs: boot sweep, a ripple on receive, a flash on send
- Runs from disk or **cartridge** (Magic Desk, boots straight in)

## Firmware — built off the Bluetooth companion

The beta ships a matching firmware, and it is built from the **BLE**
companion variant rather than the USB one. That means **both interfaces are
live at once**: a phone stays connected over Bluetooth while the C64 talks
on the user port, because the companion firmware routes them through its
own `MultiSerialInterface`.

The C64 link is set to **2400 baud** to match the client. Both ends have to
agree on the rate, so this firmware and `meshcore64-v2.prg` are a pair —
running the 2400 client against a 600-baud firmware will not work.

| file | what |
|---|---|
| `meshcore64-ble-2400-1.17.1-0679dbef-merged.bin` | **full flash at `0x0` — use this** |
| `meshcore64-ble-2400-1.17.1-0679dbef.bin` | application only, for an OTA-style update |

It is stock MeshCore v1.17.1 (commit `0679dbef`) plus four build flags on
the `Heltec_v3_companion_radio_ble` environment:

```ini
  -D SERIAL_RX=45
  -D SERIAL_TX=46
  -D HW_SERIAL_BAUD_RATE=2400
  -D HW_SERIAL_UART_NUM=2
```

`main.cpp`'s hardware-serial block is already guarded by
`#if defined(SERIAL_RX)`, so defining those is all it takes to bring the
UART up in any companion variant — the same small patch described in
[README.md](README.md) applies unchanged. Build it with:

```bash
pio run -e Heltec_v3_companion_radio_ble -t mergebin
```

> **Flashing warning, unchanged from v1:** do all of this with the Heltec
> board **out of the cartridge**. bit-zeal warns against connecting USB
> while it is seated.

## Files

| file | what |
|---|---|
| `meshcore64-v2.prg` | the client, **2400 baud** |
| `meshcore64-v2.crt` | cartridge image for emulators |
| `meshcore64-v2.bin` | flat 32K image — **burn this to a 27C256** |
| `src/mlfull.py` | assembler source and build script |
| `src/asm.py` | the 6502 assembler |
| `src/mkcart.py` | Magic Desk cartridge builder |

```bash
python3 src/mlfull.py <ctrl> out.prg <blank> <testkeys> <latadj>
#   ctrl    7=600  8=1200  10=2400  11=4800
#   blank   1 = blank the display (needed above 2400)
#   latadj  first-sample latency allowance, default 275

python3 src/mlfull.py 8 meshcore64-1200.prg 0 0 275    # a 1200 build
```

The assembler is ~250 lines of Python with no dependencies. It grew
`.word`/`.text`, `<lo`/`>hi` operators, `label+n` expressions and automatic
long-branch relaxation (an out-of-range `bcs far` becomes
`bcc over / jmp far`) to build this.

## Testing

Fourteen runs in VICE: 600/1200/2400 x REU/no-REU x PAL/NTSC, plus the
cartridge on both standards. **Zero rejected frames and zero framing errors
in every run**, video standard detected correctly every time, receive ring
never more than 7% full.

Full table, including the two anomalies and a known issue:

## What is not proven

**All testing is in VICE.** `x64sc` is cycle-exact, but a hand-rolled
bit-banged UART is exactly where emulation and real silicon can part
company — sample phase depends on real NMI dispatch latency. **This needs a
run on real hardware before anyone relies on it.** `latadj` is a build
parameter, so re-tuning is a one-number change.

**The firmware is part of the pair.** The client and the radio must agree
on the baud rate, so the 2400 client only works against the 2400 firmware
shipped here. Flashing it replaces whatever companion build is on the
board — the v1.x 600-baud firmware is still on
[`main`](https://github.com/pskerrett/meshcore64/tree/main) if you want to
go back.

**The v1.x BASIC client remains the stable one.** It is proven on real
hardware; this is not, yet.
